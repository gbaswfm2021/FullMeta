# Runtime

## Run Study

The project-root **Validate** action uses the shared document-validation service to check the active project JSON against its interpreting schema, the app's declarative `x-fullmeta-rules` program, and GS input rules. Its V-rule requires `/model/illumination/gridSize` to belong to `[64,128,256]`. The selected `/model/study/0` item has **Run Study** and **Clear Results** in Settings. Its Settings also own `iterations` (integer 1–100, default 40) and `seed` (unsigned 32-bit integer, default 20261110). Commit pending Settings edits, run shared Model Editor validation, and save valid unsaved values through the normal project Save path before calculation. Resolve the selected Study ID again from the saved snapshot. On a validation or save failure, do not start the operation. JavaScript rasterizes the saved SVG target for the command request and rejects foreground bins outside the wavelength-dependent propagating disk; the registered application-local Rust engine repeats that physical guard, evaluates the illumination expression and aperture, and performs the scalar far-field GS algorithm defined in [contracts/scalar-far-field-gs.md](contracts/scalar-far-field-gs.md). `N` is the number of square-grid samples per side; the allowed sizes are 64, 128, and 256, with 256 by 256 bundled. The stored seed initializes phase deterministically. The same engine executable provides the Study calculation and project-run storage entries. The Study operation and Graphics Console transitions are defined in [contracts/study-workflow.md](contracts/study-workflow.md).

On success, return the binary target intensity, wrapped metasurface phase, and normalized reconstructed far-field intensity arrays at the declared grid size. Before saving, require all three arrays to contain exactly `N²` entries; target and intensity entries must be finite numbers and phase entries must be finite numbers or JSON `null`. Save the accepted input snapshot and complete outputs in a unique run directory under the project's declared `gerchbergsaxton_runs/` storage. The saved `result.json` has these exact fields: `size`, `wavelengthNm`, `samplePitchUm`, `targetWidthRadPerUm`, `k0RadPerUm`, `deltaKRadPerUm`, `kExtent`, `target`, `phase`, and `intensity`. `kExtent=π/Δx`; target and intensity use row-major `N×N` far-field arrays, and phase uses the same row order on the metasurface grid. Verify the required files before marking the run completed or showing it as a saved result. Keep the two most recent completed Study runs. While Study is selected, Graphics Console displays the selected saved run's three graphics together. Settings contain the selected input controls and Study actions, not result images. The engine normalizes reconstructed intensity by its maximum propagating-bin intensity; this is relative display intensity, not calibrated power. Label target and reconstructed far-field axes using physical transverse wavevectors in rad/µm.

## Result lifecycle

- Run Study requires a saved project snapshot and runs against exactly that snapshot and the selected Study ID.
- The shared Operation strip identifies the native Rust Study calculation and exposes Stop while it is active. Stop terminates the registered command and prevents its result from being saved. Because calculation runs as one native process, progress is indeterminate until it returns; completion reports the requested iteration total.
- A successful run writes `request.json`, `result.json`, then `run.json` in its project-local run directory; publishing `run.json` last marks the directory as a completed run for the shared run-history reader. `request.json` is the exact saved project-document snapshot used for the run. `run.json` contains `runId`, `application`, `state`, `startedAt`, `completedAt`, `study` (`id` and `name`), `inputFingerprint`, and `artifacts` (`request.json` and `result.json`). `result.json` contains the exact fields listed above.
- The project retains its two most recent completed runs. The latest completed run is selected by default; the previous retained run remains selectable from the Study's **Run history** panel.
- On opening or reselecting Study, read saved run summaries and load the latest completed result from its checked artifact. Show it immediately when its saved input fingerprint matches the current project. If inputs differ, keep it available as a visibly stale prior run.
- **Clear Results** is available on the selected Study only. After confirmation naming the open project, it removes that project's retained GS run directories and refreshes run history and graphics. It is disabled during another document operation.
- Editing the target or Design parameters, or changing Study iterations or seed, marks existing outputs stale. Selecting Target SVG changes the Graphics Console to the target pattern with physical `kx`, `ky` axes; selecting Design parameters shows the beam and aperture without discarding the Study result.
- Validation or Save failure does not alter the previously saved inputs. After a successful Save, Stop or calculation failure leaves that saved snapshot intact. A prior completed run remains available and visibly stale when its fingerprint differs; partial output never replaces it or counts toward the two completed-run retention limit.
- Saved result arrays and run history are not embedded in project JSON. They are stored in the declared project-local run folders and remain available after closing or reopening the project.

The operation does not invoke a solver, mesher, external service, or fabrication tool. The application builds one Windows engine executable from `gs-rust/Cargo.toml` into the canonical application runtime directory, `applications/gerchbergsaxton/.runtime/x86_64-pc-windows-gnu/release/gs-engine.exe`. Run `node scripts/build-runtime.mjs` from the FullMeta root; each build writes to this same path and replaces the prior executable. `runtime-build.json` identifies `.runtime` as the Cargo target directory and `gs-engine` as its artifact; the schema and Windows Store package use the same output. Do not keep crate-root copies or separate Cargo target variants. The single binary accepts exactly `--run-study`, `--save-run`, or `--clear-results`, reads one JSON request from standard input, and writes one JSON response to standard output. The Study calculation runs with the project folder as its working directory; saving a run uses that run's directory as its working directory; clearing uses the project folder. JavaScript remains the editor/interface layer and does not perform FFT or GS iteration calculations.
