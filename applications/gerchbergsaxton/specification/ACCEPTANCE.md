# Acceptance

The requirements in [REQUIREMENTS.md](REQUIREMENTS.md) are complete only when both acceptance levels pass on the same identified application candidate. Use [Level 2 behavior replay protocol](contracts/behavior-replay-protocol.md) to construct disposable projects from this specification, exercise multiple input/UI combinations, and record replay evidence.

## Two-level acceptance

Both levels evaluate the Gerchberg–Saxton application and its saved schema on an identified candidate.

**Level 1 — Schema acceptance** establishes that the saved schema resolves through the application catalog and correctly declares the project tree, Settings bindings, shared widgets, validation rule, and Study actions. Perform this level in the visible Schema Editor and Model Editor. A structurally valid schema alone does not establish correct numerical behavior.

**Level 2 — Behavior replay** uses disposable project documents derived from the normative data model and scalar GS contract. Replay the bundled Letter M case and a variant case with changed target and physical/numerical inputs, exercise the relevant tree-selection and result workflows, and repeat identical cases to verify determinism. Do not use the bundled project as the only test case or treat an existing saved result as proof that a new calculation ran. The protocol defines the minimum case matrix and evidence.

A recorded PASS remains valid for the candidate it assessed; do not rerun passed checks without a relevant cause. Repeat the smallest set of checks affected by a schema, application-code, runtime, dependency, or requirement change, a reported defect, or new evidence that challenges the result. A schema metadata-only change requires schema validation but does not require numerical replay. Documentation-only or unrelated metadata changes do not invalidate behavior replay. Preserve prior evidence and record focused reruns against the changed candidate. A required check that was never run or lacks evidence remains pending, not passed.

## Level 1 — Schema acceptance

1. Confirm the application catalog resolves the registered Gerchberg-Saxton schema and package. In Schema Editor Document Settings, confirm the top-level schema author is `Jensen Li`. Run structural validation and verify tree annotations, field paths, shared widget bindings, and action bindings match [UI.md](UI.md), [DATA_MODEL.md](DATA_MODEL.md), and [contracts/study-workflow.md](contracts/study-workflow.md).
2. Use Schema Editor's declared V-rule authoring/inspection path to confirm the single grid-size rule accepts exactly 64, 128, and 256, identifies `/model/illumination/gridSize`, and displays the specified repair diagnostic. In the project-root Validate action, confirm the rule rejects 96 and accepts each supported size without changing stored inputs.
3. Create/open a structurally valid project and confirm project-root Validate reports structural JSON validation separately from application/model validation. Confirm invalid or empty targets and invalid scalar inputs produce actionable errors.

## Level 2 — Behavior replay

Execute the project and UI cases in [contracts/behavior-replay-protocol.md](contracts/behavior-replay-protocol.md). The following detailed acceptance checklist is mandatory for all applicable cases.

1. The application catalog resolves the app schema, and a new project opens with the application display name at the root and Inputs and Study directly below it in the exact order in [contracts/study-workflow.md](contracts/study-workflow.md). The editable project name remains in project metadata/settings. No extra application-name tree group appears between the root and Inputs/Study.
2. Confirm the project tree root uses the application display name (**Gerchberg-Saxton Hologram**, visually styled in uppercase), while the editable project name remains in project metadata. Inputs contains **Target SVG** followed by **Design parameters**. Select Target SVG and confirm its multiline SVG field fills the Settings value column, starts about 120 CSS pixels high, can be resized vertically, and its separate target-width field is editable. Select Design parameters; confirm its Settings bind to `/model/illumination` and expose the amplitude, aperture, wavelength, grid, and pitch controls. Select Far-field hologram study; confirm editable iterations and seed appear alongside the Run Study action. Edit and apply values, save and reopen; verify the SVG source and settings are preserved.
3. Invalid or empty targets and out-of-range scalar settings also produce actionable errors; stored inputs remain unchanged. (The schema-level V-rule checks are defined in Level 1.)
4. Select Target SVG and confirm the Graphics Console shows the binary target with physical `kx`, `ky` axes in rad/µm, Nyquist extent, configured `targetWidthRadPerUm` viewport span, and the propagating-wave circle when it intersects the plot. Confirm target letter size follows the SVG artwork-to-`viewBox` ratio and that changing its physical span changes the rasterized target, not just the axes. Select Design parameters and confirm it plots incident beam amplitude over the full physical x-y plane in µm, including outside the aperture, with the circular boundary and physical diameter. In each single-plot view, wheel zoom must scale/crop the raster and update axes, drag must pan raster and axes together, and double-click must reset; the aperture boundary must stay registered to the raster. Repeated zoom-out must stop at the original axis limits. Select the Study collection and confirm the specified overview; select the Study row before any run and confirm iterations, seed, no-result state, and Run Study action.
5. Select the Study row and run it. Confirm selection stays on the Study, the shared Operation strip identifies the active native Rust calculation and offers Stop, and the Graphics Console shows, from left to right, the metasurface phase profile, reconstructed hologram, and target hologram on success. Confirm the phase plot is transparent outside the aperture and that those result samples are JSON `null`; they are undefined, not zero-phase samples. Confirm Stop terminates the native calculation without saving a partial run.
6. With a completed result present, confirm the shared panel heading remains **Graphics Console**. Its Study subtitle identifies both metasurface `x`, `y` (µm) and far-field `kx`, `ky` (rad/µm) domains. Select Target SVG and confirm the visible note explains the SVG top-left/y-down source coordinates and Cartesian positive-`ky`-up plot; select Design parameters and confirm it shows the beam and aperture; reselect Study and confirm its three current views return without rerunning. Confirm every result plot has coordinate ticks and labels: reconstructed and target holograms use `kx`, `ky` in rad/µm; phase uses `x`, `y` in µm. Confirm wheel zoom centers on the pointer and scales/crops the raster, left-drag pans raster and axes together, double-click resets, and each plot responds independently. Repeated zoom-out in all these views must stop at each plot's original axis range. Interacting with one Study plot must repaint only that plot region; both sibling plots stay visible without blinking. Confirm these interactions work both for each plot inside the three-panel Study view and for single-plot Target SVG and Design parameters views. Confirm shared `plot-2d` raster-grid mode is used, its surface mode remains available to FEM, and Settings contains no result images.
7. For each replay project, run a deterministic target twice with identical saved inputs, Study ID, and seed. The defined phase samples and intensity arrays match within the documented absolute tolerance `1e-6` and have the declared dimensions; phase is finite within the illuminated aperture and null where effective amplitude is zero; intensity is finite and nonnegative. The target array and null mask match exactly.
8. Change the target, illumination, iterations, and seed independently after a successful run. Confirm each change marks the old Study result stale; confirm it remains visibly stale while Study is selected and a successful rerun replaces it.
9. Exercise validation failure, Save failure, Stop, and numerical failure. Confirm the operation state, selection, inputs, previous result, and Graphics Console follow the contract and no partial arrays are treated as current.
10. Open the bundled Letter M Hologram project, confirm the target preview shows M, select its Study, run it, and confirm the reconstructed far-field intensity visibly resembles the target M, with the phase, reconstruction, and target panels in the specified left-to-right order.
11. Save and reopen the Letter M project. Confirm target, settings, and Study item persist and the newest compatible completed result is restored from its project-local run directory. Confirm the two newest completed runs remain selectable, **Clear Results** removes only this project's runs after confirmation, and reopening after clearing shows the no-result state.

The project-root **Validate** action invokes shared Model Editor structural validation of the project JSON against its selected schema. Run Study reports native-operation state through the shared Operation UI; per-iteration progress is indeterminate while the single Rust process runs. Confirm JavaScript contains no FFT or GS iteration implementation, and the one application-local Rust executable provides run, save, and clear entries. The Study action follows the selected-row Settings pattern used by FEM; no application-specific field widget is required.

Record the candidate identity, each disposable project's starting JSON or digest, input values and seed, numerical tolerance, run IDs, observed results, and any failure. Do not treat a schema pass or a rendered target preview as evidence that GS ran successfully.
